# Sandesh privacy notes (0.5.0)

This documents implemented behaviour. The owner must supply a hosted policy, support contact and retention/deletion terms before publication.

Sandesh reads and writes SMS after you make it the default SMS app and grant permissions. Phone-state access identifies active SIMs. Carrier SMS travels through your mobile operator to the recipient when you tap Send. Notifications use a generic message preview.

SMS is held in Android's system SMS provider. Sandesh's private SQLite database stores stars, archives, aliases, spam flags, an app-local blocked-sender list, send/delivery receipts, pending incoming SMS and raw unsupported MMS notifications. These records can contain message content. Preferences store appearance and sending choices. Android protects this local storage; the backup password does not encrypt the running app's database. Automatic Android app-data backup/device transfer remains excluded.

Spam handling is manual and local. Messages are preserved in Android's store and excluded from Sandesh's ordinary folders. Blocked/spam SMS is not announced or notified by Sandesh. Blocking does not affect calls, carrier delivery or other messaging apps. Encrypted backups include spam flags and the blocked-sender list; restoring merges those settings rather than clearing current blocks.

Headset readout is optional and off by default. The user chooses the audio output. Automatic speech contains only the sender; message bodies require an explicit Read action with the phone unlocked. Sandesh selects an installed offline TTS voice and does not submit the text to a cloud AI service. The installed speech engine has its own behaviour and policy. Private, temporary synthesized audio files are deleted on completion/stop; stale files after a crash are removed on the next readout or uninstall. They are not included in backups. Audio-device identity and the announcement preference stay in local preferences and do not transfer through SMS backup. Readout uses a short-lived media-playback foreground service with a Stop notification, audio-focus and routing checks. Physical-device verification is required before release.

Accounts are optional. Email/password registration, login, verification, password reset and Google sign-in use Firebase Authentication and Android Credential Manager. Firebase receives account information such as email, optional name, provider identity and authentication requests. Sandesh does not put account passwords or authentication tokens into SMS backups. Firebase and Google SDKs manage authentication sessions; passwords are not stored in Sandesh preferences. Internet access supports these optional features. No advertising or analytics SDK is configured. The optional cloud AI feature uses the Firebase AI Logic SDK.

File backups are created only when requested. SMS, thread stars/archives/aliases, labels and appearance are compressed and encrypted on the phone using AES-256-GCM. PBKDF2-HMAC-SHA256 with a fresh salt and 600,000 iterations derives the key from an independent backup password. A new nonce is used for each backup. The selected Android document provider receives the encrypted file; that provider may be local storage or a cloud service chosen by you.

Cloud backup is also manual and uses the same device-side encryption. Firebase Cloud Firestore stores encrypted chunks and operational metadata (account UID, size, chunk count, digest and timestamp). Private rules restrict access to the owning verified account. A successful upload publishes a new latest snapshot and attempts to remove the preceding one. Interrupted uploads or failed cleanup can leave older encrypted records. No automatic expiry or background backup is implemented. The owner must deploy the private rules described in FIREBASE_SETUP.md before enabling cloud backup.

Backup passwords are not uploaded. Losing that password makes the backup unrecoverable; resetting your account password does not decrypt it. Backup encryption does not hide account identity, backup size or timestamps from the service operator. Backups exclude MMS/RCS, process-only drafts, pending send jobs and account credentials.

Restore requires default-SMS access, full password/integrity/format verification and confirmation. It merges history without deleting current SMS. Restored unsent messages are marked failed and never submitted for sending. Historical SIM IDs are not reused on a new phone.

Uninstalling removes app-private data and local authentication state, but does not delete system SMS, exported files, your Firebase account or cloud backups. Signing out also retains those records. Account/cloud-data deletion is not yet available in this candidate; the owner must implement an in-app deletion flow and a public deletion-request route before a store release with accounts.

Contacts access, MMS attachment transport, group MMS and RCS are unsupported. AI summaries and reply suggestions are optional and off by default. When you explicitly generate an answer, eligible text from the selected conversation is sent to Google Gemini through Firebase AI Logic. Sandesh does not add sender aliases, phone numbers, message IDs, dates or SIM metadata, but message bodies may contain identifying or sensitive information. Local filters exclude likely verification/OTP, password and financial messages, but cannot guarantee removal of every sensitive detail. Review the exact preview before sharing. Sandesh limits context to recent eligible text and does not upload the whole inbox.

Unused AI results are held in memory, not written to the app database or backups. If you send a suggested draft, the resulting SMS follows normal SMS storage and backup behaviour. Reply suggestions are drafts only; sending requires a separate user action. AI opt-in is device-specific, is not backed up, and is disabled after restore. Turning off AI or cancelling waiting does not retract text already submitted. Google and the Firebase project operator process requests under the provider terms, billing tier and monitoring/retention settings; enabling encrypted SMS backup does not encrypt AI input against the AI provider.

Firebase App Check uses installation/device attestation for AI requests. Debug builds use installation-specific debug tokens; release builds use Play Integrity. Attestation providers receive the metadata needed to verify the app/device. Local request counters limit normal app usage but do not impose a server billing cap. On-device draft tidying and offline headset readout are separate from cloud AI. Android, carriers, document providers, Google and Firebase have their own data handling outside Sandesh's local storage controls.
